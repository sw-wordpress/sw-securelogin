# ADR 005: Username-bound passkey login

- **Proof:** lbuchs/webauthn verifies type, challenge, signature, RP hash, UP/UV. The adapter additionally checks exact HTTPS origin, embedding context, credential owner, required user handle and immutable backup eligibility. Binary fields are bounded and canonical base64url.
- **Privacy:** anonymous options always omit `allowCredentials`, including for nonexistent or credentialless accounts. This intentionally replaces PLAN's credential-ID disclosure: the browser discovers a key, but the server still requires the entered username to own it. Enrollment now requires discoverable credentials. Older non-discoverable keys need re-enrollment; password recovery remains available.
- **Transactions:** 120-second, single-use proof bound to a secure HttpOnly host-only SameSite=Strict cookie; no binding secret in JSON. Username, password fingerprint, remember choice and validated admin redirect stay server-side. Password changes invalidate pending login. Reauthentication instead requires the current cookie session, REST nonce and a separate purpose; it issues only a one-use management grant.
- **Sessions/policies:** `wp_signon` runs with a temporary verified identity and final account guard; hooks are removed in `finally`. Core user/authenticate vetoes remain effective, cookie vetoes and throwing login hooks roll back the captured new session. Unknown callbacks on `authenticate`, `wp_authenticate_user`, `wp_authenticate` or `wp_login` block passkey proof until a reviewed site-specific adapter explicitly returns true on `swsl_passkey_auth_compatible` (arguments: false, affected hook names). This is a compatibility assertion, not an MFA exemption; do not blanket-enable it. Reviewed callbacks are listed in `AuthPolicy::REVIEWED` (currently WP Armour's form honeypot, which never sees JSON fields). Because such callbacks may return null instead of the user, `AuthPolicy::seeded()` restores the verified identity at priorities 1 and 19, before core callbacks; WP_Error vetoes and substitutions stay effective. Adapters for actual security/MFA plugins remain an M3 gate.
- **Concurrency/counters:** a per-user database lock covers assertion verification, usage update and session issuance; revocation/erasure take the same lock. Counter high-water marks never decrease. Regressions on device-bound keys fail; synchronized keys may continue with an anomaly counter. Signed backup state and last use are updated only after valid proof.
- **Abuse/audit:** fixed-window peer, submitted-name, site and reauthentication budgets fail closed on storage errors. Only `REMOTE_ADDR` is used; shared proxies share the peer budget. Salted bucket hashes expire within five minutes; identifier-free aggregate proof/failure/anomaly counters expire at the daily boundary. `login_verified` counts verified assertions, not necessarily issued sessions. Hourly cleanup removes expired records; no request payloads, IPs or account names are logged.
- **Verification:** signed positive/negative fixtures, REST/session/policy/locking tests and Chromium with two independent virtual authenticators. Real devices, Firefox/Safari, proxy deployments and actual MFA plugins remain release checks. Sources: [WebAuthn verification/privacy](https://www.w3.org/TR/webauthn-3/), [WordPress sign-on](https://developer.wordpress.org/reference/functions/wp_signon/).
- **Login UI:** with script, the form starts in passkey mode (username/email plus passkey button); "Log in with password" reveals the unchanged core form and re-enables `#user_pass`, which core `user-profile.js` disables while hidden. Without script or WebAuthn support, or after a core login error, the password form is shown. Accounts resolve by login name, then email address, as in core.
