# Verifizierte, ausschließlich manuelle GitHub-Updates

Adaptiert aus [ChurchTools Suite 49dc66f](https://github.com/sw-wordpress/churchtools-suite/tree/49dc66f), inklusive `includes/update/*`, Signierer, Workflows und Testfällen. Die native Pluginzeile folgt sw-backupit. Es wird kein Code zur Laufzeit aus anderen Checkouts geladen.

Verbindliche Quelle: `sw-wordpress/sw-securelogin`, GitHub-Repository-ID **1439006733** (GitHub-API geprüft), Slug `sw-securelogin`, Hauptdatei `sw-securelogin.php`, Basename `sw-securelogin/sw-securelogin.php`, Version `SWSL_VERSION`. Nur dieses Einzelplugin wird verwaltet. ZIP: `sw-securelogin-X.Y.Z.zip`, Stammordner `sw-securelogin/`. Stabile Tags `[v]X.Y.Z` entsprechen exakt Header, Konstante und Stable tag.

`src/Update/` enthält Manifest-, Paket-, HTTP-, Status-/Lock-, Service- und WordPress-Adapter. `Config/source.php`, `descriptors.php`, `trusted-keys.php` verankern Identität und öffentliche Schlüssel lokal. Schlüsselkonstante `SWSL_RELEASE_PUBLIC_KEYS`, Filter `swsl_verified_release_public_keys`/`swsl_verified_update_descriptors`, Optionen `swsl_verified_github_updates_v1`/`swsl_verified_github_updates_lock_v1`/`swsl_verified_updates_migrated`, AJAX `swsl_check_github_updates`, Nonce `swsl_verified_updates`, Handle `swsl-verified-updates`, Global `swslVerifiedUpdates`, DOM `swsl-verified-updates-*` kollidieren nicht mit ChurchTools oder sw-backupit.

Kein HTTP und keine eigenen Update-DB-Abfragen im Frontend. Anzeigen lesen lokalen Cache. Backend-Prüfung erst nach `load`, mit Nonce, Berechtigung, 24-Stunden-Limit, manuell 60 Sekunden. Fehler verbrauchen einen Versuch; persistenter nicht autoloadender Zustand überlebt Transient-Löschung. Netzwerkweite atomare Lease mit Eigentümerprüfung und 120 Sekunden Laufzeit; Ergebnisübernahme und Lock-Übernahme verwenden denselben Mutex; ohne GET_LOCK-Unterstützung sicher gesperrt. Installation nur durch native autorisierte WordPress-Aktionen; Cron, REST, CLI und Automatic-Upgrader bleiben gesperrt. Fremde Plugins und Angebote bleiben unberührt.

Ed25519 über exakte Manifestbytes, ausschließlich lokale Vertrauensanker. Bindungen: Repository/ID, Release-ID/Tag, Commitformat, Asset-ID, Name, Größe, SHA-256, Slug, Version, Hauptdatei und Mindestversionen. Doppelte JSON-Schlüssel und uneindeutige Assets werden abgelehnt. Kein Unsigned-/Hash-only-Fallback. Höchste akzeptierte Version persistent; Cache maximal sieben Tage.

HTTP: nur HTTPS/443 ohne Userinfo, genaue GitHub-/CDN-Hostliste, vier geprüfte Redirects, fünf Sekunden je Metadatenrequest, 60 Sekunden Download, 256 KiB Manifest, 1 KiB Signatur, 50 MiB ZIP. Vor Core-Extraktion erneute Signaturprüfung, Hash/Größe, ein Stammordner, sichere Pfade und Dateitypen, keine Duplikate/Symlinks/verschlüsselten Einträge, maximal 10.000 Einträge/250 MiB entpackt, Kompressionsgrenze und passende Plugin-Header. Temporäre Dateien 0600 und Cleanup; WordPress übernimmt Extraktion und Installation.

[Schlüsseleinrichtung und Betrieb](GITHUB-UPDATES-BETRIEB.md), [Tests](TESTING.md), [Release-Abnahmen](RELEASE.md). Der Betreiber hat den produktiven öffentlichen Schlüssel im Checkout eingerichtet. Eine produktiv aktive Updateversorgung ist weiterhin nicht verifiziert: Schutzregeln, vertrauenswürdige Erstverteilung und signierter Release müssen abgeschlossen sein.
